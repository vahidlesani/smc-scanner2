> هر سرویس) از داخل سندباکس قابل خواندن نیست: API ریلوی و هاست لاگ گیت‌هاب مسدود است.

## ۳) آنچه کد نشان می‌دهد (مسیرهای داغ)
- **اسکن کشف کامل هر ۱۵ دقیقه** (`main.py::run_discovery_scan`، کامنت کد: «اولین اسکن ~۱۱ دقیقه»).
  یعنی ~۷۳٪ زمان دیوار، CPU مشغول است.
- **پاس اسپات هر ۶۰ دقیقه** (`SPOT_SYMBOL_LIMIT=24` × ۶ TF، ~۸٫۵ دقیقه).
- **رندر چارت** هنوز پیش‌فرض ON است (`config.py: chart_enabled=True`). طبق یادداشت خود پروژه
  (HANDOFF r59.3) هر چارت ~۱٫۵–۲ ثانیه CPU و حدود ۲MB PNG (Egress تلگرام) است.
- **سقف نماد** `WATCHLIST_MAX_SYMBOLS=100` (پیش‌فرض).
- **مانیتور کاندیداها هر ۱۰ ثانیه** (در بیکاری ۲۰ ثانیه) + **line-watch** هر ~۳۰ ثانیه.
- **اتصال Postgres در هر تماس** (بدون pool): `database/db.py::get_conn` و `candidate_store._connection`.
  محاسبه‌ام: چند ده هزار اتصال در روز، که هزینه‌ی دلاری‌اش **چند سنت در روز** است؛ پس
  اولویت پایین است و این بار تغییرش ندادم (ریسک بدون سود قابل‌توجه).

## ۴) چیزهایی که از کد **نمی‌توانم** بفهمم
1. تعداد سرویس‌های فعال در پروژهٔ Railway (آیا هنوز **دو بوت** زنده است؟ — README رفرنس ۱۰-۱۲ می‌گوید بله).
2. مصرف هر سرویس جدا (CPU/RAM/Egress) در ۹ ساعت گذشته.
3. هاست `DATABASE_URL`: اگر `*.proxy.rlwy.net` (عمومی) باشد، ترافیک DB هزینهٔ Egress دارد؛
   باید `postgres.railway.internal` (داخلی) باشد. (`ops/railway/ops.sh` هم همین را ترجیح می‌دهد.)
4. متغیرهای `CHART_ENABLED`, `WATCHLIST_MAX_SYMBOLS`, `FULL_SCAN_MINUTES` در اکانت جدید.

## ۵) چک‌لیست برای Viva (۵ دقیقه)
1. Railway → پروژه → **تعداد سرویس‌های با Deployment فعال.** انتظار: **یک** اسکنر (combined) + **یک** Postgres.
   اگر دو اسکنر دیدید، یکی را **Remove/Stop** کنید (این فقط با شماست؛ من به Railway دسترسی ندارم).
2. Railway → هر سرویس → **Metrics/Usage** (۹ ساعت گذشته): کدام CPU/RAM/Egress بالاست؟
3. Variables سرویس اسکنر: `DATABASE_URL` را نگاه کنید (host). اگر `proxy.rlwy.net` بود، بگویید تا عوضش کنیم.
4. GitHub → Actions → **railway-ops** → اجرای `38148023423` → job `ops` → step `run`. خروجی `usage` را
   کپی کنید و برای من بفرستید (من این لاگ را از سندباکس نمی‌توانم بخوانم).

## ۶) تصمیم بعدی بر اساس نتیجه
| یافته | اقدام |
|---|---|
| دو اسکنر فعال | یکی را متوقف کنید → تقریباً نصف هزینه |
| DB روی host عمومی | `DATABASE_URL` را به `*.railway.internal` تغییر دهید |
| اسکنر تنها، CPU بالا | کاهش `WATCHLIST_MAX_SYMBOLS` (مثلاً 100→40) یا `FULL_SCAN_MINUTES`. **این تصمیم محصول است** (تعداد سیگنال‌ها کم می‌شود)؛ منتظر حکم شما می‌مانم. |
| Egress بالا | بررسی حجم عکس‌های تلگرام و polling وب‌اپ |

## ۷) تغییر کدی که در این نوبت انجام شد
- فقط نانس اجرای ورک‌فلو (`ops/railway/request.json`) برای گرفتن گزارش `usage` بالا رفت.
- **هیچ تغییر منطق اسکنر یا چارت برای هزینه انجام نشد** (هدف: تغییری که قانون‌ها را نشکند و عدد واقعی را ببیند).
