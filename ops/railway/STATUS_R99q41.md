# R99q41 — وضعیت لحظه‌ای مهاجرت به اکانت جدید ریلیوی

> این فایل نقطهٔ حقیقتِ مهاجرت است. هر بار که وضعیت عوض شد، همین‌جا به‌روز می‌شود.

## چرا مهاجرت متوقف است (مدرک، نه حدس)

توکن اکانت جدید **معتبر است** — API آن را می‌شناسد (خطای احراز هویت نمی‌دهد) و
`projects` را خالی برمی‌گرداند (ورک‌اسپیس تازه، بدون پروژه). اما هر تلاش برای
ساخت پروژه این را برمی‌گرداند:

```
projectCreate → BAD_USER_INPUT
  "Deploys have been paused temporarily"
```

این پیام **محدودیت اکانت نیست؛ وقفهٔ پلتفرمیِ ریلیوی در سطح Free/Hobby** است.
مستند رسمی (`docs.railway.com/deployments/reference#deployments-paused---limited-access`):

- در دوره‌های فشار، ریلیوی ابتدا منابع را به Pro/Enterprise می‌دهد و **ساخت و
  استقرار Free و به‌ندرت Hobby را موقتاً معلق** می‌کند.
- در زمان وقفه: نشان «Limited Access» در داشبورد، دیپلوی‌های جدید **صف**
  می‌شوند، بقیهٔ امکانات کار می‌کند، **هیچ داده یا دیپلوی موجودی آسیب نمی‌بیند**.
- پس از رفع: صف به‌ترتیب خودکار اجرا می‌شود؛ «هیچ اقدامی لازم نیست».
- فقط ارتقا به Pro صف را دور می‌زند.

در همین لحظه چند رشتهٔ فعال در `station.railway.com` هم همین را گزارش می‌کنند.
پس **نه توکن بد است، نه اکانت بن شده، نه کد.**

> تفکیک مهم: اکانت **قدیمی** پیام دیگری داشت — «We limited this workspace after
> detecting unusual activity» — که آن یکی واقعاً محدودیتِ همان ورک‌اسپیس بود و
> با مهاجرت حل می‌شود. اکانت **جدید** فقط در صفِ پلتفرمی است.

## وقتی صف باز شد، دقیقاً این اجرا می‌شود

```bash
cd smc-scanner2
RAILWAY_API_TOKEN=<new> python ops/railway/migrate_r99q41.py \
    --apply --deploy \
    --env-file /home/user/.viva_secrets/env_r99q41.json
```

می‌سازد: پروژه `viva-signals` → محیط `production` → سرویس `smc-scanner2`
(بدون سورس) → متغیرها (`skipDeploys=true`) → سیاست `ON_FAILURE×10`، ۱ رپلیکا،
`/health` → `serviceConnect(repo=release)` → **یک** دیپلوی.

اگر `serviceConnect` به‌خاطر نبودِ GitHub App روی اکانت جدید رد شد، مسیر جانشین:

```bash
export PATH=/home/user/.npm-global/bin:$PATH
RAILWAY_API_TOKEN=<new> railway link --project viva-signals --environment production --service smc-scanner2
RAILWAY_API_TOKEN=<new> railway up --ci      # آپلود مستقیم سورس، بدون نیاز به GitHub
```

`railway up` سورس را از همین ماشین آپلود می‌کند و **به اتصال GitHub اصلاً نیاز
ندارد** — همان چیزی که وقتی «به ریپو وصل نمی‌شوم» می‌خواهیم.

## بهینه‌سازی مصرف (درخواست او: «مصرف رو بهینه کن»)

| اقدام | اثر |
|---|---|
| خودکار‌دیپلویِ GitHub خاموش | ۱۱۰ دیپلویِ چند روز → ۱ دیپلوی برای هر ریلیز |
| `release` اسکوش | هر ریلیز = یک بیلد، نه N بیلد برای N کامیت |
| `RAILWAY_DEPLOYMENT_OVERLAP_SECONDS=0` | در زمان دیپلوی دو کانتینر هم‌زمان billed نشوند |
| `RAILWAY_DEPLOYMENT_DRAINING_SECONDS=10` | خاموشیِ سریعِ نسخهٔ قبلی |
| ۱ رپلیکا، `ON_FAILURE ×10` | بدون رپلیکای اضافه، بدون حلقهٔ ری‌استارت |
| منطقهٔ `europe-west4` | نزدیک به اروپا (همان قبلی) |

**حساب سرانگشتیِ مصرف:** ریلیوی ~$10 به‌ازای هر GB-ماه حافظه می‌گیرد. یک کانتینر
همیشه‌روشن با ۰٫۵ GB ≈ **$۵ در ماه**، یعنی کل اعتبار Trial/Hobby را می‌خورد. پس
اگر بخواهیم در همان $۵ بمانیم، مصرف حافظه باید نزدیک ۰٫۵ GB بماند؛ هر دیپلویِ
اضافی هم بیلد-دقیقه و هم چرخشِ کانتینر اضافه می‌کند — که با سیاستِ بالا حذف شد.

## آنچه از او لازم است

1. **`TELEGRAM_TOKEN`** — بدون آن ربات بالا می‌آید ولی هیچ پیامی نمی‌فرستد
   (`main.py:3627` فقط هشدار می‌دهد). هر جای دیگری از سکرت‌ها لازم شد بگو.
2. اگر می‌خواهد زودتر از صف بیرون بیاید: ارتقا به Pro صف را کامل دور می‌زند؛
   وگرنه چند ساعت صبر، خودش حل می‌شود.
3. برای مسیر GitHub (اگر CLI را نمی‌خواهد): در GitHub → Settings → Applications،
   **Railway GitHub App** را برای اکانت جدید نصب و ریپو `vahidlesani/smc-scanner2`
   را به آن grant کند — بعد `serviceConnect` کار می‌کند.

# به‌روزرسانی ۱۰-۲۱ (بعد از فایل متغیرها)

## ۶) «تعداد زیاد متغیرها محدودیت می‌آورد؟» — نه؛ آنچه محدودیت آورد **تعداد دیپلوی‌ها** بود

فایل `variables-production.env.txt` را شمردم:

| دسته | تعداد |
|---|---|
| کل کلیدهای فایل | ۷۱ |
| کلیدهای تزریقیِ خودِ ریلوی (`RAILWAY_*`) که **کپی نمی‌شوند** | ۱۱ |
| **متغیر واقعی که روی سرویس جدید ست می‌شود** | **۶۲** (۶۰ اپ + ۲ کلید هزینه) |
| نام‌های دیگری که کد می‌خواند ولی روی سرویس قدیم هم مقدار نداشتند (پیش‌فرض کد) | ۱۱۰ |

- مستند ریلوی **هیچ سقفی برای تعداد متغیر** اعلام نمی‌کند؛ مقدار چندخطی هم مجاز است.
  سرویس قدیم با همین ۷۱ کلید ماه‌ها کار می‌کرد.
- چیزی که اکانت را سوزاند، تعداد متغیر نبود؛ **تعداد بیلد** بود: ۱۱۰ دیپلوی، یکی
  برای هر پوش. ضمناً در ریلوی **هر افزودن/ویرایش متغیر یک تغییرِ استیج‌شده و یک
  دیپلوی** است — یعنی ۶۲ متغیر را اگر دستی یکی‌یکی در داشبورد بزنی، تا ۶۲ دیپلوی.
- راه‌حل در ابزار ما: همهٔ ۶۲ متغیر در **یک** فراخوانی `variableCollectionUpsert`
  با `skipDeploys: true` نوشته می‌شوند، بعد **یک** دیپلوی. یعنی ۶۲ متغیر = ۱ بیلد.

## ۷) «با گیت‌هاب وصل شوم، می‌رود به اکانت اول» — بله، و راهش این است

ریلوی هویتِ ورود را به همان اکانتی می‌بندد که با آن ثبت‌نام شده. پس:

1. **با GitHub لاگین نکن.** اول از حساب جدید **خارج** شو، بعد با
   `zhiva.mon@atomicmail.io` و رمز (یا Google) وارد شو — نه دکمهٔ «Continue with GitHub».
2. داخل همان اکانت: **Account Settings → Connect GitHub**. اگر کلیک روی این دکمه
   دوباره به اکانت قدیم پرتت کرد، یعنی نشستِ مرورگر به اکانتِ گیت‌هابی وصل است؛
   کاملاً Sign out کن، با ایمیل وارد شو، بعد Connect.
3. بعد از اتصال، در GitHub → Settings → Applications → **Railway → Configure**،
   ریپوی `vahidlesani/smc-scanner2` را برای همین نصب (installation) grant کن.
4. اگر نصبِ اپ هنوز به اکانت قدیم چسبیده: در اکانت قدیم Railway آن را **Uninstall**
   کن، بعد از اکانت جدید دوباره Connect کن تا installation تازه ساخته شود.

**راه بی‌دردسر (توصیه):** اصلاً GitHub را وصل نکن. `railway up` سورس را از
همین ماشین آپلود می‌کند و به GitHub App نیاز ندارد؛ بعد از هر ریلیز هم فقط یک
دیسپچ می‌زنی. دستورش در بخش «وقتی صف باز شد».
